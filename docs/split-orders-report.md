# 商品拆分：数据模型、订单口径与风险报告

> 调研对象：`server/src/lib/split.js`、`server/src/routes/order.js`、`server/src/lib/settle.js`
> 调研方式：代码路径逐行核对 + 独立库实测（`split-audit.db`，未触碰主库）
> 结论先行：**已支付的订单不受影响；未支付的订单会按拆分前的旧价成交，并多吃掉一个名额，造成超卖。**

---

## 一、拆分到底改了什么

拆分只动 `goods` 表的 6 个字段，**一行订单都不碰**：

```
is_split        = 1        拆分标记（不可逆）
split_total     = N        拆分份数
stock_total     = N        名额
stock_num       = N        剩余名额
goods_min_price = 每份价
line_price      = 每份划线价
```

每份价的计算：

```
每份价 = floor(总价 × 100 ÷ N) ÷ 100        // 换成分 → 除以份数 → 向下取整 → 换回元
```

划线价同一公式。向下取整产生的零头**被截掉**，既不给卖家也不进平台账，卖家全额卖完会比原价少几分。

**关键点：拆分不是「生成 N 个新商品」，而是「同一个商品，把可售名额从 1 改成 N」。**

---

## 二、用户手里的订单怎么算

订单分为三类，处理方式完全不同：

### 第一类：拆分前已支付的订单 —— 完全不受影响

拆分有前置条件 `goods_status === 10`（在售）。一件货成交后 `settleOrder()` 会立刻把它置为 20（下架）并转移给买家，**所以只要有过成交，这件货当时就拆不了**。

订单自身的 `price`、`total_price`、`seller_id` 都是成交当时写死的快照，之后商品怎么改都不影响它。买家看到的历史订单、卖家看到的入账，都不会因为拆分而变动。

唯一的例外路径是「成交 → 买家转拍 → 商品回到在售」，这时新持有人（或后台）可以拆。但那是另一轮商品了，上一手的订单已经结清，不受影响。

### 第二类：拆分后产生的订单 —— 每份一笔

| 字段 | 取值 |
|---|---|
| `price` | 每份价 |
| `num` | 本次抢几份 |
| `total_price` | 每份价 × 份数 |
| `seller_id` | 原持有人（整件不转移） |
| 结算 | `settleOrder()` 走按件分支：名额减一、销量加一，**不换持有人、不下架** |

卖家每卖出一份收一份的钱，卖光 N 份收 `N × 每份价`，与拆分前的整件总价基本相等（差零头）。

### 第三类：拆分前已下单但未支付的订单 —— **问题在这里**

这类订单的 `price` 是**拆分前的整件价**，它不会因为拆分而重新计算。同时它在拆分前已经通过 `deductStock()` 占用了一个名额，而拆分代码里是：

```js
UPDATE goods SET ... stock_num = ?, ... WHERE goods_id = ?
```

**无条件覆盖**，把被占用的那份一起抹掉了。

## 三、实测证据（独立库，非主库）

准备：一件单价 ¥1000、名额 10 的在售商品。

| 步骤 | stock_num / stock_total | 说明 |
|---|---|---|
| 初始 | 10 / 10 | |
| A 下单 1 件，**不付款** | **9** / 10 | 下单即占名额 |
| 后台拆成 5 份 | **5** / 5 | 名额被重置，A 占的那份凭空消失 |
| B 买下 5 份并支付 | 0 / 5 | 商品随即下架 |
| A 支付拆分前的旧单 | 0 / 5 | **依然成功**，再卖出 1 份 |

结果：

```
商品声明的总名额      5
实际成交份数          7 份 / 3 笔     ← 含一笔历史订单
超卖                  2 份
销量 sales_actual     6
```

订单实际长这样：

| 订单 | 下单价 | 数量 | 总额 | 下单时点 |
|---|---|---|---|---|
| #2 | ¥1000 | 1 | ¥1000 | **拆分前**（整件价） |
| #3 | ¥200 | 5 | ¥1000 | 拆分后（每份价） |

两个后果：

1. **超卖**：声明的 5 份，实际卖出 6~7 份，仓库里的货不够发。
2. **价格不公**：A 花 ¥1000 买到的是「1 个名额」，而拆分后同样一个名额只值 ¥200，A 多付了 ¥800。

## 四、其他值得注意的点

| # | 现象 | 影响 |
|---|---|---|
| 1 | 拆分**不可撤销**，`is_split` 不在后台可编辑字段里 | 拆错份数（比如该拆 2 份拆成 100 份）只能重建商品 |
| 2 | 拆分商品禁止转拍，但**拆分前遗留的转拍挂单记录仍然开着**（`orders.consignment_status = 10`） | 流拍扫描（`scanStreambeat`）会把正在按份售卖的商品判为流拍并下架 |
| 3 | `sales_actual` 保留拆分前的历史销量 | 无法用「已售 / 总份数」算进度，只能看 `stock_num` |
| 4 | 直推奖、积分奖励按**每一份订单**单独计算并向下取整 | 拆得越细，零头损耗越多（拆 100 份时损耗明显） |
| 5 | 会员端的「拆分订单」(`/order/toSplitOrder`) 是**订单级**操作，与商品拆分无关 | 两个功能同名，运营容易混淆 |

## 五、建议

### 必修：拆分前置校验未支付订单

```js
const pending = get(
  "SELECT COUNT(*) c FROM orders WHERE goods_id = ? AND type = 1 AND status = 0",
  g.goods_id,
);
if (Number(pending.c) > 0) {
  return { ok: false, reason: `还有 ${pending.c} 笔待付款订单，先处理完再拆分` };
}
```

理由：拆分是把整件货拆开卖。已经有人按整件价下单，就不该再拆——要么拒绝，要么把那些订单按比例重算金额（后者涉及改已下单的金额，风险更高，不建议）。

### 建议：拆分时清理遗留的转拍挂单

```js
run('UPDATE orders SET consignment_status = 0 WHERE goods_id = ? AND consignment_status = 10', g.goods_id);
```

否则流拍扫描会把按份售卖中的商品强制下架。

### 可选：零头补给最后一份

```js
// 前 N-1 份向下取整，最后一份 = 总价 - 每份价 × (N-1)，总额刚好对齐
```

### 可选：支持撤销拆分

新增 `/admin/api/goods/unsplit`，条件是「一份都没卖出去」（`stock_num = stock_total`），回滚 `is_split`、`split_total`、价格。

---

## 六、一句话总结

拆分是**商品维度**的定价与名额改造，不碰订单。已成交的订单天然安全（成交即下架，拆不了）；真正的缺口是**拆分时没拦住待付款订单**——那些订单会按旧价成交，并且因为 `stock_num` 被重置而多吃名额，导致超卖。加一条前置校验即可堵住。
