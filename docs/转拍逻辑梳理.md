# 转拍（转单）业务逻辑梳理

> 梳理对象：抢购 → 确认 → 转拍 → 到顶回收 的完整资金与货物链路
> 代码基线：`4a9a1fe` 之后（2026-10-31）
> 本文只描述**现状实现**，不含改造建议；风险点集中在最后一节

---

## 一、名词与角色

| 名词 | 含义 |
|---|---|
| 抢购单 | `orders.type = 1`，唯一参与转拍的订单类型 |
| 按件卖（一批货） | `goods.stock_total > 1`，多个会员各抢 1 件、名额递减，**不支持转拍** |
| 唯一件 | `goods.stock_total = 1`，成交即整件过户给买家，**只有它能转拍** |
| 转拍 | 持有人把手上这件货重新挂牌，等下一手买走（原站称之为「寄卖」） |
| 到顶 | 下一轮涨价会越过「价格上限」，系统判定不能再转拍 |
| 平台接盘 | 到顶后平台按当前实际价格买下这件货，货转平台持仓 |

| 角色 | 能做什么 |
|---|---|
| 买家（普通会员） | 抢单、申请抢单（`pay_type=0`，等后台确认）、转拍自己持有的货 |
| 平台（后台运营） | 确认收款（真正成交）、取消订单、处置回收/封顶商品 |
| 系统 | 超时关单、到期下架、到顶回收、发站内信 |

## 二、状态机

### 订单 `orders`

```
status:      0 待付款 ──确认──> 10 待发货(实为「已成交」) ──> 30 已完成
                 │                      
                 ├──用户取消/超时关闭──> 40 已取消
pay_status:  0 未确认 ──确认──> 10 已确认
consignment_status: 0 未挂牌 ──转拍──> 10 在挂（到期自动归 0）
```

> `ORDER_STATUS` 字典里的「待发货 / 待收货」是历史遗留文案，发货环节已整体下线，
> 前台与后台统一只按 `pay_status` 显示「待确认 / 已确认」。

### 商品 `goods`

```
goods_status: 10 上架 ⇄ 20 下架
member_id:    0 平台持仓 / >0 会员持有
recycled:     0 正常 / 1 已到顶回收（前台不再展示）
area_date:    '' 不限日期 / YYYY-MM-DD 该日开抢
```

## 三、完整链路（一步一步）

### 1. 下单 `POST /api/order/toAddOrder`（`routes/order.js`）

服务端按顺序做 11 道校验，任一不通过即拒：

| # | 校验 | 失败提示 |
|---|---|---|
| 1 | 支付方式开放（`pay_type=0` 跳过） | 该支付方式暂未开放 |
| 2 | 商品存在且 `goods_status=10` | 商品已下架 |
| 3 | 不能买自己持有的货 | 不能购买自己持有的商品 |
| 4 | `area_date` 不能是未来 | 该商品将在 X 的场次开抢 |
| 5 | `num` 必须是 1 | 每件商品每人限购 1 件 |
| 6 | **一人一货终身一次**（未取消的订单里已存在即拒） | 这件商品你已经买过了 |
| 7 | 场次此刻开放（支持「提前抢购」lead 秒） | 当前不在抢购时间内 / 场次已结束 |
| 8 | 本场限购（**跨商品合计**，按场次 + 日期） | 本场每人限购 N 件，你已抢 X 件 |
| 9 | 锁单：唯一件不能已有待付款单 | 已被抢先锁定 |
| 10 | 强制收款方式（可配） | 请先设置收款方式 |
| 11 | 按件卖时扣名额（原子） | 只剩 N 个名额了 |

通过后写一条订单：`status=0, pay_status=0, seller_id=商品当前持有人, specialarea_id=当前开放场次`。

### 2. 成交（两条路径，殊途同归）

- **H5 自助**：`toPay(pay_type=0)` 只写一条「申请抢单」日志（幂等），**不改任何状态**；余额支付（`pay_type=1`）则当场扣款 + `settleOrder`。
- **后台确认**：`POST /admin/api/orders/confirm-pay` → `confirmPayOne()`
  1. 凭证校验（`pay_voucher_required` 开启且 `pay_type` 不是 0/1 时必须传凭证）
  2. `goodsStillOwnedBySeller()`：这件货必须还在订单上的卖家手里
  3. 原子 `UPDATE ... WHERE pay_status = 0`（并发只成功一次）
  4. `settleOrder(o)` 结算
  5. 写「确认收款」日志

### 3. 结算 `settleOrder()`（`lib/settle.js`）

| 动作 | 唯一件 | 按件卖 |
|---|---|---|
| 商品 | 持有人 = 买家、`turn_beat_num +1`、销量 +1、**下架**（等转拍再上架） | 只加销量；名额扣完才下架，持有人不变 |
| 卖家 | 收**全额货款**（平台不从货款抽成）+「商品售出」流水 | 同左 |
| 上级 | 直推奖 = `订单总额 × drive_award_rate%`，进佣金账户 | 同左 |
| 买家 | 按配置送积分（默认关） | 同左 |

> 唯一件成交后**必须下架**：留在场次里别人能按原价再抢一次（等于白送一轮）。

### 4. 转拍 `POST /api/order/consignment`（核心）

**准入条件**（`routes/order.js:500`）：

1. 订单属于本人，且 `status` 为 10 或 30
2. `consignment_status != 10`（没在挂）
3. 商品不是按件卖（`stock_total = 1`）
4. 商品当前持有人 = 本人
5. **未到顶**：`priceCapOf(g).reached = false`
6. **在转拍时限内**：`支付时间 + 场次 transposition_hours`（0 = 不限）

**定价**（`quoteConsignment()`）：

```
上一手价 prevPrice   = 订单 total_price
上一手成本 prevCost  = total_price + service_charge
下一轮标价 nextPrice = prevPrice × (1 + price_increase_rate%)   ← 逐轮复利
                    （涨价率为 0 时用前端传的价，或商品现价）
兜底：nextPrice = min(nextPrice, 价格上限)
上架费 listingFee    = prevPrice × listing_fee_rate%（默认 2.8%）
持有人净收入        = nextPrice − prevCost − listingFee
```

**执行**（单事务）：

1. 扣上架费（`amount - fee`，余额不足直接拒；费率为 0 不扣也不写 0 元流水）
2. 原订单 `consignment_status=10`、写入 `listing_fee`、`transposition_time`
3. 商品：改标价、重新上架（`goods_status=10, is_sell=10`）、`area_date = 下一场日期`
4. **场次关联覆盖为唯一场次**（`setGoodsAreas([下一场])`）——不追加，否则同一件货会在旧场次按旧价再被抢
5. 写「转拍上架」日志

> 不生成 `type=2` 寄卖单：挂单信息已完整存在订单与商品两处，另开一张单曾留下永不结清的僵尸单。

**落场规则** `nextSlot(currentId, baseDate, at)`（`lib/sessions.js`）：

- 按场次 `start_time` 排序，从当前场次往后找
- **跳过今天已经结束的场次**（17:30 从上午场转拍 → 落到晚间场，不是已结束的下午场）
- 当天全部结束 → 次日第一场
- 已排到未来某天 → 不再受当前时间影响

### 5. 到顶与回收（`lib/recycle.js`）

**到顶判定**（`lib/priceCap.js`）：

```
涨价率 > 0：下一轮价 > 价格上限 → 到顶（不是等当前价追平上限）
涨价率 = 0：当前价 >= 价格上限 → 到顶
```

**扫描**：`price_cap > 0` + `member_id > 0` + `goods_status ∈ {10, 20}` + 无回收记录

**结算**：按**商品当前实际价格**接盘（刚买下未转拍 → 按买入价；已挂牌 → 按挂牌价）

- 持有人 `amount + recyclePrice`，写「系统回收」流水
- 商品：`member_id=0, goods_status=20, recycled=1, area_date=''`，清空场次关联
- 写 `goods_recycle` 台账 + 订单日志 + 站内信

**两条闸门**：`recycle_open`（总开关）、`recycle_daily_cap`（日限额，超了只记「待处理」不打款）

### 6. 到期下架（`lib/expire.js`，替代已下线的「流拍」）

商品 `area_date <= 今天`、在架、会员持有、未回收，且**关联的场次都不再开放**（今天也没有「未开始」的场次）：

- 商品下架 → 持有人手上（货还在）
- `consignment_status` 归 0 → 持有人可以重新转拍
- 发站内信告知

### 7. 取消与超时

| 场景 | 触发 | 结果 |
|---|---|---|
| 用户取消 | `POST /order/cancel`，仅 `status=0` | `status=40`，退回名额 |
| 超时关单 | 定时任务扫 `type∈{1,3} & status=0 & pay_status=0` 超过 `order_pay_timeout`（默认 30 分钟） | `status=40`，退回名额，发站内信 |
| 后台取消 | `/admin/api/orders/cancel` | 同上，可批量 |

## 四、资金与价格公式汇总

```
成交一次：
  买家支出 = 商品价 + 抢单服务费(商品价 × service_charge%)
  卖家收入 = 商品价（全额，不抽成）
  平台收入 = 抢单服务费 − 直推奖(商品价 × drive_award_rate%)

转拍一次：
  持有人支出 = 上架费(上一手价 × listing_fee_rate%)
  持有人收入 = 下一轮标价（卖出时全额）
  平台收入 = 上架费 − 直推奖(下一轮标价 × drive_award_rate%)

一轮的净收益（持有人视角）：
  nextPrice − (prevPrice + prevService) − listingFee
  示例：10000 买入、服务费 0、涨价 3%、上架费 2.8%
       下一轮 10300，收回 10300，成本 10000 + 280 = 10280 → 净赚 20
```

> 结论：**涨价率必须大于「上架费率 + 抢单服务费率」**，持有人才真正赚钱，否则每转一手都在亏。

## 五、关键约束一览

| 约束 | 值 | 位置 |
|---|---|---|
| 一次下单件数 | 固定 1 | `order.js` |
| 同一件货每人可买次数 | 终身 1 次（取消后可重抢） | `order.js` |
| 每场每人限购 | 场次配置 `buy_num`（默认 10），**跨商品合计、按场次+日期** | `lib/purchaseLimit.js` |
| 锁单 | 唯一件只允许一笔待付款单 | `order.js` |
| 转拍时限 | 场次 `transposition_hours`（0=不限） | `order.js` |
| 转拍次数上限 | 由价格上限间接决定 | `lib/priceCap.js` |
| 出场后能否再买 | 不能（终身一次） | `order.js` |

## 六、配置项（后台「交易设置」）

| key | 含义 | 默认 |
|---|---|---|
| `service_charge` | 抢单服务费 %（买家额外付） | 0 |
| `price_increase_rate` | 转拍涨价率 %（逐轮复利） | 3 |
| `listing_fee_rate` | 转拍上架费 % | 2.8 |
| `drive_award_rate` | 直推奖 % | 0.5 |
| `order_pay_timeout` | 未确认关单时限（分钟） | 30 |
| `recycle_open` | 到顶自动回收开关 | 开 |
| `recycle_daily_cap` | 每日回收上限（0=不限） | 0 |
| `pay_voucher_required` | 确认时是否必须有支付凭证 | 开 |
| `require_receiving_account` | 抢单前是否必须设收款方式 | 关 |

## 八、边界与风险点（供决策，不含改造）

1. **买家池单调递减**
   「同一件货每人终身只能买一次」+ 转拍链，意味着每转一手就少一个潜在买家。
   一个商品的流转次数上限 ≈ 会员总数 − 1，且必须是不同的人。

2. **到顶回收可能让持有人净亏**
   刚买入就封顶（买入价已贴着上限）时，平台按「当前实际价格」= 买入价接盘，
   持有人白付了抢单服务费。若此时又没转拍，上架费为 0，净亏 = 服务费。

3. **转拍需要余额**
   上架费从余额扣，余额不足无法转拍，货只能拿在手上等到期下架。系统没有「欠费转拍」或提醒充值。

4. **锁单只覆盖唯一件**
   按件卖的商品不锁单，并发支付靠 `goodsStillOwnedBySeller()` 兜底（先到先得，后付报错）。

5. **`area_date` 是隐藏字段**
   转拍后商品被排到「下一场」，若下一场是明天，今天前台就不显示。
   后台商品表单里该字段只读隐藏，运营看不到（场次配置页已能看到，商品页看不到）。

6. **场次时段被改动会影响落场**
   若把某场次的结束时间拉长到 23:59，`nextSlot` 会认为它仍在开放，落场结果随之改变。

7. **`ORDER_STATUS` 字典与前台文案不一致**
   字典里仍是「待发货 / 待收货」，后台若干位置若回退使用它，会显示已下线环节的文案。

8. **一人一货一次 + 转拍 = 无法回购**
   原持有人即使货已流通到别人手里，也不能再买回来。若业务上允许「回购」，需单独开口子。
