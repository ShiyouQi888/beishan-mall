## 二、高危漏洞

### 2.1 【高】停用场次后，商品照样能买 —— `is_open` 没参与下单校验

> **状态：已修复（2026-10-31）**  
> 改动点：`openAreaOf()` 跳过 `is_open != 10` 的场次；`LIST_VISIBLE` 增加「至少有一个启用场次」条件；  
> `getLootGoodsList` 的场次子查询带上 `is_open` 过滤；下单失败时给出「该商品所在场次已停用」的准确提示。  
> 验证：`scripts/probe/area-disabled.mjs` 15 项断言（含「自由商品不被误伤」与「双挂场次仍可买」）。

配置页原文写着「停用后本场不出现在前台抢购页，**也不参与下单校验**」。实测只做到前半句的一半。

**复现**（独立库，场次 1 设 `is_open=20`、时段设全天、关联商品 1）：

```
A. H5 抢购列表里能看到？  是（未按启用状态过滤）
B. 停用场次后能否下单？   成功（停用场次照样能买）
```

**代码证据**：

| 位置                                   | 问题                                                         |
| ------------------------------------ | ---------------------------------------------------------- |
| `lib/areaGoods.js:11 areasOfGoods()` | `JOIN specialarea` 后**不过滤 `is_open`**                      |
| `lib/areaGoods.js:50 openAreaOf()`   | 只调 `sessionWindow()` 判断时间窗，**不看 `is_open`**                |
| `routes/goods.js:20 LIST_VISIBLE`    | 只判断 `recycled / goods_status / area_date`，**不看 `is_open`** |
| `lib/sessions.js activeSessions()`   | 唯一过滤 `is_open=10` 的地方，只服务「场次列表接口」                          |

**影响**：运营以为关掉的场次，商品还在首页/分类/搜索里挂着，会员点进去照样下单成交。  
「停用」目前等价于「从场次选择器里隐藏」，不是真正的下架。

**建议方向**：`areasOfGoods` / `openAreaOf` / `LIST_VISIBLE` 三处统一按 `is_open=10` 过滤；  
或者干脆承认「停用=隐藏」，把配置页文案改掉。

---

### 2.2 【高】转拍货的场次被移除/删除后，货会永久卡死

> **状态：已修复（2026-10-31）**  
> 处理方式最终定为「**先拦截、再兜底**」：  
> ① 场内还有在挂牌的转拍货时，移除商品与删除场次都会被拒绝，并提示先去商品管理下架；  
> ② 后台把转拍货下架时自动解除挂牌，运营再回来移除/删场次即可；  
> ③ 到期扫描对「无场次 + 在挂」的历史脏数据仍然自动退货（`lib/listing.js releaseListing()`），  
> 保证不会再有货凭空消失。  
> 验证：`scripts/probe/listing-release.mjs` 33 项断言。

**触发路径**（两条，都很容易被点到）：

1. 场次页「关联商品」列表里点「移除」
2. 商品管理里删除该场次

**结果**：`specialarea_goods` 关联被删，但**商品的 `area_date` 和订单的 `consignment_status=10` 都原样保留**。

于是这件货进入死锁：

| 环节                  | 表现                                                                     |
| ------------------- | ---------------------------------------------------------------------- |
| H5 列表               | `area_date` 是明天 → 当天不显示                                                |
| 到期下架 `expireUnsold` | `if (!areas.length) continue`（`lib/expire.js:33`）→ 无场次直接跳过，**永远不会被下架** |
| 会员点转拍               | `consignment_status === 10` → 拒绝「该订单已转拍上架」                             |
| 后台                  | 只能手工改库或改商品状态才能救回来                                                      |

**代码证据**：`removeGoodsFromArea()`（`lib/areaGoods.js:142`）只做 `DELETE` + `syncAreaMirror`，  
不碰 `goods.area_date`，也不碰 `orders.consignment_status`；`clearAreaLinks()` 同样。

**影响**：一件货凭空消失，持有人钱货两空，且系统里没有任何入口能恢复。

**建议方向**：移除关联时，若商品处于「会员持有 + 在架 + 已挂牌」，拒绝操作并提示先去下架/等它到期；  
或移除时一并把 `consignment_status` 归 0、`area_date` 清空，让它退回「未挂牌」状态。

### 2.3 场次时段重叠：每场独立计数（设计如此，非缺陷）

> **结论：业务确认无需修改。** 限购是「**本场次**」的额度，不是「每天」的总额度，两场重叠时各算各的才是正确语义。

限购的统计口径是 `member_id + specialarea_id + 当天`（`lib/purchaseLimit.js`）。所以两场时段重叠时（比如上午 08:00-23:59 与下午 13:00-23:59 同时开）：

- 会员在 A 场买满 10 件
- 去 B 场还能再买 10 件 —— **这是设计意图**：两场各有自己的名额
- 同一件货仍受「一人一货终身一次」保护，不会重复买同一件

初版复盘把这条当成漏洞，是把「每场限购」误读成了「每天限购」。业务上确认：**场次之间不共享额度**。

**运营需知悉的一点**（不是 bug）：配出重叠时段时，"本场限购 10 件"要按「每场 10 件」理解，而不是「当天总共 10 件」。若不希望叠加，就别让两个场次的时段重叠。

## 三、错误 / Bug

### 3.1 结束时间早于开始时间，后端不拦

> **状态：已修复（2026-10-31）**  
> `POST /:module/save` 对 specialarea 增加校验：范围 00:00-23:59、`end = 0` 视为不限、  
> 否则必须 `end > start`；编辑只传单个字段时用「库里值 + 本次提交」合并后判断，避免局部更新绕过。  
> 列表页编辑弹窗也补了同款前端提示。验证：`scripts/probe/specialarea-time.mjs` 15 项断言。

- 配置页有前端校验（`SpecialareaConfig.vue` save：`et <= st` 报错）
- **列表页的编辑弹窗没有**：`ListPage.vue` 的 `timesec` 只做 `hmToSec(v)` 赋值，无比较
- 后端通用 save 也没有任何校验

**后果**（实测）：`start=20:00 / end=08:00` 的场次，`sessionWindow` 算出  
`timeOk = nowSec >= startsAt && nowSec <= endsAt` 恒为 false → 该场次**任何时刻都不可用**，  
状态在「未开始 / 已结束」之间来回，运营只会觉得「这场怎么点不进去」。

### 3.2 开放日一个都不选，等于每天都开

|                                      |   |                                        |
| ------------------------------------ | - | -------------------------------------- |
| \`sessionWindow.dayOk = !days.length |   | days.includes(today)\` —— 空数组被当成「不限制」。 |

实测：`open_days=''` 在周六 09:00 → `dayOk=true, state=open`。  
配置页靠前端兜底（全不选会强制回填 1-7），但接口直接传空串就会存成「每天开放」，与「一个都不选=都不开」的直觉相反。

### 3.3 旧订单的「已挂牌」标记永不归零

> **状态：已修复（2026-10-31）**  
> `settleOrder()` 在过户时把这件商品上所有 `consignment_status=10` 清零（含刚被买走的那一手）；  
> 新增 `listing.cleanStaleListingFlags()` 在启动时清理历史脏数据（只清「货已不在订单会员手上」的，  
> 当前持有人的合法在挂不受影响）。演示库启动后从 4 条在挂降到 2 条。  
> 验证：`scripts/probe/listing-flag.mjs` 24 项断言。

`settleOrder()` 把货过户给买家时，**没有把上一手订单的 `consignment_status` 归 0**。

演示库实测（同一件货挂了两条「在挂」记录）：

```
goods 5：order 17（会员3）+ order 21（会员2）都 = 10
goods 6：order 1（会员2）+ order 23（会员3）都 = 10
```

目前靠「转拍订单列表额外要求 `g.member_id = o.member_id`」兜住了，所以列表没重复；  
但订单维度的「是否在挂」已经不可信，任何按 `consignment_status` 统计的地方都会多算。

### 3.4 场次时间改了，已挂商品的开抢日期不跟着变

`goods.area_date` 是在转拍那一刻按「下一场」算死的。之后运营把场次时间改到别的时段，  
商品的 `area_date` 不变，可能落在已经过去的日期上 → 商品既不显示、也不会被到期下架（因为 `area_date <= 今天` 时会走 expire，  
但如果日期被改到未来则一直挂着）。

## 四、矛盾 / 名不副实

### 4.1 「转拍延长时间」不是延长，是限时

> **状态：已修复（2026-10-31）**  
> ① 配置页字段名改为「转拍时限(小时)」，与列表页、手工文档统一；  
> ② 更要紧的是**把硬拦改成了软约束**：原实现超过时限直接拒绝转拍，货会永久卡在持有人手里  
> （不能挂牌、卖不掉、下架后再点转拍还是被拦）。现在超时照常允许挂牌，只在订单动态记一笔「超时挂牌」。  
> 验证：`scripts/probe/transpose-overdue.mjs` 10 项断言。

字段名 `transposition_hours`、配置页叫「转拍延长时间(小时)」，提示写「0 = 不限」。

实际实现（`order.js` consignment）：

```js
deadline = pay_time + limitHours 小时
if (Date.now() > deadline) 拒绝「已超过转拍时限」
```

是**支付后 N 小时内必须转拍**的截止窗口，不是「延长」。语义反了，运营容易理解成「可以晚点再转」。

### 4.2 「排序」几乎不起作用

> **状态：已修复（2026-10-31）**
> 排序字段已下线：排序链改为 状态 → 开始时间 → 场次标识 → id，配置页、后台列表、H5 出参都不再带 sort。
> 场次先后完全由开始时间决定（上午→下午→晚上），不会再出现「改了数字没反应」的情况。
> 验证：`scripts/probe/admin-cleanup.mjs` 18 项（含「排序字段已移除」断言）。

配置页写「数字越小越靠前」。实际排序链（`lib/sessions.js orderSessions`）：

```
场次状态(open→upcoming→ended→closed) → start_time → name 语义 → sort → id
```

`sort` 排在第 4 位，只有「状态相同 + 开始时间相同 + name 相同」时才生效。  
两个正常配置的场次开始时间不同，改 `sort` 完全看不出变化。

### 4.3 「场次标识」后台改不了，但排序依赖它

> **状态：已修复（2026-10-31）**
> 排序链去掉 `NAME_RANK`：场次先后只看 开始时间 → id（同时段的按创建先后），
> `M.specialarea` 的 hide 字段、后台列表 orderBy 里的 `CASE name` 一并移除。
> name 列保留（seed 仍在写）但代码不再读取，新建场次 name 为空也不影响任何顺序。
> 验证：`scripts/probe/specialarea-time.mjs` 新增 5 项（合计 25 项）。

`name`（forenoon/afternoon/evening）在 `M.specialarea` 里是 `hide: true`，配置页也没有这一项。

但排序规则里 `NAME_RANK` 用它做语义排序。结果：

- seed 的三场有 name，排序正常
- **后台新建的场次 name 为空**，落到 `ELSE 9`，语义排序失效

### 4.4 配置页要求「专区图片必传」，列表页弹窗不要求

配置页 save 里有 `if (!form.image_ordinary) return ElMessage.warning('请上传专区图片')`；  
列表页的通用编辑弹窗没有这条，可以存出「没有专区图」的场次 → H5 场次横幅空白。

同一条数据，两个编辑入口，校验不一致。

### 4.5 「商品数」列与关联页可能不同步

> **状态：已修复（2026-10-31）**  
> 差异的真正来源是**关联表里的孤儿行**（商品已删、关联还在）：列表统计只数关联表，  
> 配置页明细要 JOIN goods 才能显示名称，孤儿行被 JOIN 掉。  
> 现在两边都 JOIN goods，口径一致；并新增 `areaGoods.cleanOrphanLinks()` 在启动时清理孤儿关联。  
> 验证：`scripts/probe/specialarea-time.mjs` 新增 5 项断言（合计 20 项）。

`M.specialarea` 的 `area_goods_count` 是列表页的统计列，配置页顶部显示的是 `goodsList.length`。  
两者来自不同查询（一个是聚合，一个是明细列表），理论上应一致，但列表页不刷新时看到的可能是旧值。  
属于展示层的小不一致，不影响业务。

### 4.6 `buy_num` 的默认值与下限两处不一致

> **状态：已修复（2026-10-31）**
> 统一为「最小 1、最大 999、默认 10」：表默认值改成 10（与 seed、配置页一致）；
> `M.specialarea` 的字段带 `min/max`，通用弹窗也按字段上下限渲染（原来固定 min=0，能存 0）；
> 后端 save 增加校验，`< 1` 或 `> 999` 直接拒。`sessionLimitOf` 的 `<=0 = 不限` 仅作为历史脏数据兜底。
> 验证：`scripts/probe/specialarea-time.mjs` 新增 7 项（合计 32 项）。

- 表结构默认 `1`（`schema.sql`）
- seed 里三场都是 `10`
- 配置页 `:min="1"`
- 通用弹窗走 `el-input-number :min="0"` → **可以存 0**
- 而 `sessionLimitOf()` 把 `<= 0` 当「不限」

所以「0」在配置页填不进去，在列表弹窗能填，且含义是「不限购」。三处口径不统一。

## 五、死字段 / 无效配置

### 5.1 「开放预约」`is_subscribe` 是空开关

> **状态：已修复（2026-10-31）** 配置页开关与后台字段定义一并移除，表列保留并标注「已下线」。

全项目搜索：除了 `specialarea` 表的字段定义、seed、出参透传、配置页的开关本身，**没有任何业务代码消费它**。  
H5 没有预约页面、没有预约接口、没有「已预约」状态。

运营打开它，前台什么都不会发生。

### 5.2 `title_intro` / `image_intro` 是废弃字段

> **状态：已修复（2026-10-31）** `areaPayload` 不再透传 `introduction_title` / `introduction_images`，
> 表列保留并标注「已下线，前台不渲染」。

表里有，`areaPayload` 透传为 `introduction_title` / `introduction_images`，  
但 H5 全站没有任何地方渲染这两个字段；配置页也不提供编辑入口。

### 5.3 「场次图」与「专区图」概念重叠

> **状态：已修复（2026-10-31）** 配置页字段名统一为「场次图」，hint 明说「只有这一张，
> 抢购页场次卡和商品详情顶部共用，不需要另配」；`image_intro` 不再参与出参。

`image_ordinary` 同时被当作场次卡图和详情横幅用（H5 按 3:1 展示），  
而 `image_intro` 闲置。字段命名容易让运营以为有两张图要配。
