## 一、流拍（streambeat）

### 1.1 依据

| 线索 | 来源 |
|---|---|
| 后台独立菜单「流拍订单」`order.streambeat/index` | 后台菜单树 |
| 操作按钮：订单详情 / 前去发货 / **审核成功 / 审核拒绝 / 释放订单** | 该页面 HTML |
| 列表列：商品信息 / 单价数量 / 付款信息 / 用户信息 / 交易状态 | 该页面 HTML 列定义 |
| `goods_status` 存在「上架/下架」之外的状态（后台筛选含多值） | 商品列表筛选器 |

### 1.2 推断逻辑

"流拍"在拍卖语境 = **标的无人应价，未能成交**。在本系统里对应：

> 场次结束后，已转拍挂出、但商品仍由原持有人持有的，判定为流拍。

**数据源（后续重构）**：最初实现靠一张独立的 `type=2` 寄卖挂单来记录"已挂出"，
但该单据与「`goods` 的持有人/标价/上下架」+「原订单的 `consignment_status` / `transposition_time`」
完全重复，且成交后不会结清，会留下买家为空的僵尸记录。现已取消该单据，
流拍改为直接从原订单推导：

```sql
-- 挂了但没卖掉：订单标记已转拍 + 商品仍归该买家 + 仍在架
o.consignment_status = 10 AND o.type = 1 AND o.status IN (10,30)
AND g.member_id = o.member_id AND g.goods_status = 10
AND IFNULL(o.transposition_time, o.create_time) <= <结算日 23:59:59>
```

判为流拍后：生成 `type=5` 流拍记录、商品置 `goods_status=30`、原订单 `consignment_status` 归 0（关闭挂单）。
因为挂单标记会被清零，同一挂单不会被重复判流拍（幂等）。

处理：商品下架（`goods_status=30`），生成一条流拍记录（`orders.type=5`），持有人可在后台「释放订单」把商品退回可售状态。

**不确定点**：原站流拍是否需要人工审核（有「审核成功/拒绝」按钮，推测是审核后才算正式流拍）。本实现采用「自动标记 + 后台可释放」，不引入审核态。

### 1.3 实现

- `goods.goods_status` 新增 `30 = 流拍`
- 结算时（`runSettlement`）自动扫描：场次已结束 + 挂单未成交 → 标记流拍
- 手工触发接口：`POST /admin/api/streambeat/scan`
- 释放：`POST /admin/api/streambeat/release` → 商品恢复 `goods_status=10`，流拍单置为已释放

## 二、拆分（split）

### 2.1 依据

| 线索 | 来源 |
|---|---|
| `goods.is_split` 字段 + 后台「拆分商品」独立菜单 | 后台菜单 + 列表列 |
| 拆分商品列表有「实际库存」「是否拆分」「转拍次数」列 | `goods.split/index` 列定义 |
| 订单详情 H5 有 `1==t.detail.is_split` 的判断分支 | H5 分包 `pages-order-orderdetail` |
| 接口 `/order/toSplitOrder`（参数 `order_id`） | 116 接口清单 |

### 2.2 推断逻辑

两处功能互相印证：

**（A）商品维度拆分**：一件高价值商品按份出售，降低参与门槛。
- `is_split=1` + `stock_num=N`（可售份数）
- 每份价格 = 商品价（`goods_min_price` 即单价）
- 购买时扣减份数，售罄下架

**（B）订单维度拆分**：持有人把自己一笔多份的订单拆成多笔，便于分别转拍。

本实现两者都做，以（A）为主、（B）为辅。**不确定点**：原站的拆分是按"份数"还是按"金额"，是否有最小单位限制。

### 2.3 实现

- `goods.split_total`（拆分总份数）
- 拆分接口：`POST /goods/split`（持有人/后台），把商品按 N 份挂牌
- 下单时原子扣减 `stock_num`，不足则拒单
- `stock_num` 归零 → 自动下架（`goods_status=20`）
