# 原站业务规格书（实证版）

> 本文所有结论都来自原站实际数据/接口/配置，不包含推测。凡未验证的项都标注了「未确认」。

---

## 一、核心模型：不是电商，是「标的物加价转售 + 平台抽成」

商品不是库存，是**可流转的标的物**。同一件商品在会员之间反复易手，每次易手平台抽一次费。

关键字段（`goods` 表）：

| 字段 | 含义 | 证据 |
|---|---|---|
| `member_id` | 现持有人 | 后台商品列表"现持有人/现持有人手机号"两列 |
| `turn_beat_num` | 转拍次数 | 后台"拆分商品"列表有"转拍次数"列 |
| `goods_min_price` | 当前售卖价 | 转拍时可改价 |
| `specialarea_id` | 所属场次 | 首页接口按场次聚合商品 |

## 二、资金算法（已用真实数据验证）

### 2.1 收费项

| 费用 | 费率 | 收取时机 | 计算基数 |
|---|---|---|---|
| **上架费** | **2.8%** | 转拍（寄卖上架）时 | 本轮抢购金额 |
| **直推奖** | **0.5%** | 每笔买单成交 | 买单金额 |
| 团队奖 | 0%（五级全为 0） | — | — |
| 平级奖 | 0% | — | — |

**抢购本身不收费。**

### 2.2 证据一：中账原始记录（member 409 张三）

```
buy_amount            5000.00    ← 本轮抢购合计
consignment_amount   15404.00    ← 本轮卖出合计
listing_fee_amount     140.00    ← 上架费
listing_fee_percentage   2.8     ← 费率（接口直接返回）
balance              10404.00    ← 收支差额
```

两条恒等式：

```
140.00  = 5000 × 2.8%              （上架费按抢购额算）
10404.00 = 15404 − 5000            （差额 = 卖出 − 买入）
```

大账里张三的 5 笔卖单（1060 + 8699 + 2525 + 2120 + 1000 = **15404**）与中账完全吻合。

### 2.3 证据二：直推奖反推

佣金流水（`finance.energy`，`type=3` 返佣）实际只有两条：

| 佣金 | ÷0.5% | ÷1% | ÷2.8% |
|---|---|---|---|
| 4.81 | **962.00** ✓ 整数 | 481.00 | 171.79 |
| 8.00 | **1600.00** ✓ 整数 | 800.00 | 285.71 |

只有 0.5% 能同时得出两个整数买单金额，与配置 `grade[drive_award]=0.5` 完全一致。

备注文案："会员16690970730大账买单直推奖" —— 明确了「买单 × 直推奖」。

### 2.4 完整分账链路

以 5000 元一轮为例：

```
买家付 5000 ──────────────────→ 卖家收 5000（全额，不扣费）
买家另付 140（2.8% 上架费）───→ 平台
                                   ├─ 25.00 → 直接上级（5000 × 0.5%）
                                   └─ 115.00 → 平台净留存（2.3%）
```

**平台每轮净赚 2.3%，永远不会亏。** 参与者必须让售价 > 买入价 × 1.028 才能保本——这是这套模式的核心驱动力。

## 三、会员等级体系

配置位置：后台「邀请配置」（`setting/grade`），实际取值：

| 等级 | 直推人数 | 团队有效 | 团队流水(万) | 团队奖 |
|---|---|---|---|---|
| 普通会员 | 1 | – | – | 0 |
| 白银级 | 1 | 1 | 5 | 0 |
| 黄金级 | 1 | 1 | 10 | 0 |
| 砖石级 | 1 | 1 | 20 | 0 |
| 王者级 | 1 | 1 | 30 | 0 |

`grade[drive_award] = 0.5`（直推奖 %）
`grade[same_level_award] = 0`（平级奖 %）

**结论：三级分销有代码框架但未启用**，实际只跑单级 0.5% 直推奖。

## 四、订单状态维度

订单不是单一状态机，而是**四个并行维度**（订单详情页实证）：

| 维度 | 取值示例 |
|---|---|
| 付款状态 | 待付款 / 已付款 |
| 发货状态 | 待发货 / 已发货 |
| 收货状态 | 待收货 / 已收货 |
| **拼团（寄卖）状态** | **未寄卖 / 寄卖中 / 已寄卖** |

订单金额展示为「实付款（含运费）」，支付方式含「银行卡支付」。

## 五、结算机制：差价匹配（核心）

这是整套系统最关键、也最容易被漏掉的环节。**平台不经手任何资金**，只做撮合。

### 5.1 流程

```
场次结束
  ↓
统计每人「买入总额」与「卖出总额」
  ↓
差额 balance = 卖出 − 买入   （正 = 应收，负 = 应付）
  ↓
应付方与应收方做差价匹配，生成付款单
  ↓
买家线下转账 → 上传凭证 → 卖家确认收款
```

### 5.2 实证（原站中账数据，member 409 张三）

| 字段 | 值 | 含义 |
|---|---|---|
| `buy_amount` | 5000.00 | 本轮买入合计（1 笔买单） |
| `consignment_amount` | 15404.00 | 本轮卖出合计（5 笔卖单） |
| `balance` | 10404.00 | 应收 = 15404 − 5000 |
| `buy_order_ids` | `98` | 关联的买单ID |
| `sell_order_ids` | `56,63,64,65,89` | 关联的卖单ID |

平台账号（member 1）：买入 124965，卖出 0，`balance = -124965`（应付）——它是全场最大买家。

### 5.3 三本账的对应关系

| 账目 | 粒度 | 内容 |
|---|---|---|
| **大账** | 单笔订单 | 每笔订单对买家是「买单」、对卖家是「卖单」，`pay_price` 正=收款 负=付款 |
| **中账** | 每人每结算周期 | 上述买入/卖出汇总 + 差额 + 上架费 |
| **小账** | 每笔匹配 | 谁付给谁、多少钱、凭证、确认状态 |

### 5.4 为什么必须有线下凭证

因为差价匹配后是**会员之间互相转账**，平台不托管资金。所以必须有「上传凭证 → 对方确认」这一环，否则无法证明钱已到账。这也解释了为什么原站 `order.pay/small` 会有「确认收款」按钮。

## 六、三类账目

| 账目 | 用途 | 关键字段 |
|---|---|---|
| **大账-结算** | 每笔订单的资金流水 | `order_no`、`order_type_text`(买单/卖单)、`pay_price`(正=收款 负=付款) |
| **中账-差额** | 按会员汇总一轮周期的买卖差额 | `buy_amount`、`consignment_amount`、`listing_fee_amount`、`listing_fee_percentage`、`coupon_reward`、`balance`、`buy_order_ids`、`sell_order_ids` |
| **小账-凭证** | 线下转账人工确认 | 付款人/收款人/金额/付款方式/付款凭证/付款状态 |

小账有「确认收款」按钮，说明**支付未闭环，靠线下转账 + 人工核销**。

## 八、接口设计

- 无版本前缀，全部裸在根路径：`/goods/getLootList`、`/order/toAddOrder`
- 鉴权：`token` 请求头（JWT，`member_info` 存 member_id）
- 版本：`Version: 102` 请求头
- 响应：`{ code, msg, data }`，`code: 1` 成功、`0` 业务失败、`-1` 未登录、`-10` 支付未配置、`-500` 签名失败
- 部分敏感接口（如 `/order/getServiceCharge`）额外要求签名，前端封装中未见签名代码 —— **签名算法未确认**
